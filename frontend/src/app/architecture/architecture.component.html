Report request flow

  1. Browser loads the Angular app (this demo serves static assets only).
  2. In a full stack run, the UI calls GET/POST/PUT/DELETE /api/v1/reports.
  3. Reverse proxy forwards to Play; filters attach X-Request-ID, security headers, rate limits, and audit logs.
  4. ReportController delegates to ReportRepository (Slick → PostgreSQL).
  5. JSON response returns paginated data + pagination matching OpenAPI.

CI, Docker, and k6 exercise or package the system; they are not part of the live request path.

Performance evidence

The following figures are repository-documented results from 2026-01-09. This showcase did not re-run the load tests.

  • Workload: k6 against GET /api/v1/reports, ~4 minutes, ramp to 10 then 20 VUs, 1000 reports seeded — see perf/baseline-results.md and perf/improvement-results.md.
  • Documented baseline avg latency 187 ms (p95 487 ms); after changes, documented avg 142 ms (p95 342 ms). Environment: local http://localhost:9000, k6 v0.47.0.
  • Raw k6 JSON output is not committed; reproducibility details beyond the markdown summaries and perf/load-test.js are limited.
  • Index caveat: migration database/migrations/002_add_gin_index.sql defines a GIN index on to_tsvector(...), while ReportRepository still filters with SQL LIKE '%…%'. A tsvector GIN index is not used by those LIKE operators; documented GIN-related gains for filter queries should be treated with that limitation. Parallel count/data queries and the created_at DESC index remain consistent with the code.
